# プロパティ統制語彙（4手がかりの語彙固定）

要約：frontmatter をあとで付ける飾りでなくデータの唯一の正とみなす。type と status の取りうる値を固定し、種類ごとの追加プロパティを標準化しておくと、後で Bases / Dataview を入れたとき、frontmatter を書き直さずに使える。[[命名と4手がかり]] の補足で、語彙の置き場はこのページに集約する。

## type の統制語彙（この値だけ使う）
日々の記録
- 会議録 / 顧客メモ / インタビュー / 調査 / 意思決定 / 提案

知識の常設ページ
- 概念 / 人物 / フレームワーク / ベンチマーク / プレイブック / 論点 / 業界プロファイル / 事例 / 動向 / 参考 / 案件

Vault の骨組み
- 索引 / 概要 / 規約 / 説明

新しい種類が要るときは、ここに1語追加してから使う（勝手に増やさない）。

## status の統制語彙
進行中 / 完了 / 保留 / 参照用 / 廃止
- 引き出しで頻繁に使う軸。進行中だけ・完了を除く で絞れる
- 常設の概念・テンプレ・カタログは 参照用 を既定にする
- 廃止：規約変更などで前提が崩れ無効になったが、履歴として残すノート（2026-07-16、規約撤廃に伴い追加）

## 種類ごとの追加プロパティ（標準）
- 提案 … deadline（日付）/ priority（高・中・低）
- 意思決定 … decided（日付）/ decision（一文）
- 顧客メモ … company / next_action
- 人物 … company / role
- 案件 … client / status
- 事例・動向・ベンチマーク … source / last_verified
- 概念（MOC） … tags に MOC を含める

## 信頼レイヤー（事実を貯めるノートに足す任意項目）
事実を蓄積するノート（調査・事例・業界プロファイル・ベンチマーク・参考）には、4つの手がかりを壊さずに次を足せる。
- source … 一次/二次情報のURL（本文併記でもよい）
- last_verified … 最後に人手で確かめた日（ISO）
- certainty … 確実 / 有力 / 仮説 / 未確認
- owner … その事実の責任者（複数人で書く共有Vaultのとき）

確認できない事実は書かないか certainty: 未確認 と明記する。

## なぜ値を固定するのか
- frontmatter を唯一の正にすると Bases / Dataview がそのまま効く。逆に語彙がゆらぐと表が半分空のまま使えない … https://danholloran.me/posts/obsidian-properties-and-frontmatter-a-practical-guide （2026-06-03）
- 型をそろえる（日付は ISO、チェックは boolean）と並べ替え・絞り込みが安定する

## Bases 昇格パス（プラグイン解禁時）
- この語彙を守っていれば、index.md を Bases の動くダッシュボードへ昇格させても frontmatter を書き直さずに済む … 公式 https://obsidian.md/help/bases
- 例：type: 提案 を deadline で並べる進捗ボード、status で絞る案件一覧
- 解禁前は Markdown のまま。昇格は任意の上位互換
